11. **独立审计由独立审计对话负责。** 开发代理不得自我审计；独立审计通过不等于用户验收。

## 1. 产品定位：这是个人自用软件

WorkManager 是一款供用户自己使用的 Windows 本地工作管理软件，不是商业化 SaaS，不面向公众销售，也不承担企业级、多租户或团队协作需求。

开发成功标准只有一个：**可靠、简单地满足用户已经确认的实际使用需求。**

除非用户明确提出，不做以下工作：

- 不为其他用户、企业客户、管理员或多角色预留功能。
- 不增加云同步、账号体系、多人协作、通用权限框架或远程服务。
- 不为“以后可能会用到”预留扩展点、插件体系、配置项或抽象层。
- 不试图覆盖所有理论边界、罕见环境和假设性故障。
- 不把个人软件按商业产品上市标准进行过度架构、过度测试或过度文档化。

这不代表可以忽略真实风险。个人数据的完整性、隐私、安全、便携路径和用户明确要求的功能仍然必须可靠。独立代码审计、安全审计和用户验收继续遵循各自的审计/验收任务说明；本开发理念不降低其文档读取、证据复核或验收标准。

## 2. 最小完整实现：只做当前任务需要的事

每个任务都按最小完整变更执行：

1. **先确认需求存在。** 只实现当前任务说明、PRD、已确认决策或用户当前指令明确要求的内容。
2. **先读现有代码。** 找到真实调用链、现有组件、工具函数和项目约定；优先复用，不另造一套。
3. **选择最简单的完整方案。** 优先使用现有实现、标准库、Windows/Tauri 原生能力和已安装依赖。
4. **限制修改范围。** 只改完成任务所需的文件；不顺带重构无关模块、不改无关命名、不清理无关代码。
5. **拒绝无需求的复杂度。** 不增加没有当前用例支撑的抽象、包装层、管理器、适配器、配置开关、泛型框架、依赖或兼容分支。
6. **不为少写代码而制造难读代码。** 目标是最小、清晰、可维护的完整实现，不是机械压缩行数。

如果两个方案都能满足已确认需求，优先选择新增代码更少、依赖更少、理解成本更低、后续维护更简单的方案。

**交付单位是完整业务闭环，不是孤立代码片段。** 一个任务至少要打通其所需的 UI、IPC、Core、数据库和验证链路；不能把只有页面没有数据、只有接口没有业务规则、或只有自测没有证据的半成品当作完成。完整的业务闭环仍然以最小实现为前提，不因此扩大范围或引入不必要抽象。

## 3. 不允许以“个人自用”为由省略的质量底线

以下内容不可为了减少代码或测试而删除：

- 用户明确要求的功能、业务规则和验收条件。
- 输入信任边界上的必要校验。
- 防止数据损坏、覆盖、丢失或误删的错误处理。
- 数据库事务、migration 回滚和已有数据兼容性。
- 本地数据隐私、便携目录边界和已确认的安全约束。
- 用户原始附件不得被程序擅自删除、移动或修改。
- 能让用户理解并恢复的关键失败提示。
- 现有架构边界和已确认的 DEC 决策。

“只考虑自己的使用”意味着不做虚构需求，不意味着忽略真实数据风险。

## 4. 测试与验证：按风险做，不按数量做

- 每个代码任务都要验证本次改动实际影响的核心路径。
- 新增分支、循环、解析、状态流转、事务、持久化或安全逻辑时，优先添加一个小而有效的测试。
- Bug 修复先建立能复现该 Bug 的反馈环，再修根因，并保留必要的回归测试。
- 简单改名、文档修改、无逻辑的样式或机械调整，不强制增加专门测试；按影响范围运行必要检查。
- 对数据库、文件系统、数据清理、备份恢复、路径安全和其他可能导致数据丢失的逻辑，必须验证真实关键边界。
- 不要求 100% 覆盖率，不以测试数量为目标，不穷举没有现实影响的理论场景。
- 不为了测试而引入新的测试框架、依赖或复杂测试基础设施；先使用仓库已有工具。
- 测试结果必须如实报告。未测内容和已知风险必须明确列出。
- 上述“按风险做”只用于开发过程中的实现测试，不减少独立审计/安全审计/最终验收任务要求的独立证据检查。

## 6. 每次开发任务的最小流程

1. 阅读 `AGENTS.md`、本文件、当前任务说明和必要的权威文档。
2. 检查 Git 工作区、当前分支、基线 commit 和未提交改动。
3. 明确本任务目标、最小修改范围、必要调用方、核心验收点和不做的事项。
4. 加载 Ponytail 与 Matt Pocock Implement Skill；按需加载 TDD、Bug 诊断或 Code Review。
5. 先复用现有实现，再做最小代码修改；不扩大任务范围。
6. 运行与改动风险匹配的验证；代码任务按项目规范完成必要质量门禁。
7. 审查 diff：删除不必要代码，检查需求遗漏、回归、数据风险和测试证据。
8. 更新任务要求的状态、报告和 GitHub 记录；如实说明未覆盖内容与风险。

简单任务不必机械地产生设计报告、测试计划、架构图或大量新文档。只有当复杂度、数据风险或用户要求确实需要时才增加这些产物。

## 7. 任务交付时必须说明

- 本次真正实现了什么，修改了哪些文件。
- 采用的最小实现方案，以及复用了哪些已有能力。
- 实际加载的两个 Skill 文件及上游 commit SHA（或无法加载的原因）。
- 实际运行的测试/检查命令及结果；没有运行的内容明确写“未运行”。
- 明确没有实现的额外场景，以及这样做的理由。
- 尚存风险、未验证假设和回滚/恢复注意事项（如适用）。

## 8. 独立审计、用户验收与 GitHub 合并门禁

- **独立审计由独立审计对话负责。** 开发代理自己写代码、自己运行测试，不构成独立审计。
- **独立审计与合并门禁分开管理。** 独立审计可以继续进行，但审计通过不代表允许合并。
- **不擅自合并任何 PR。** 合并 PR 是用户权限；任何 AI Agent 都不得自行合并 PR #8、PR #9 或其他 PR。
- **P2-01 合并门禁（用户 2026-11-25 确认方案 A）：**
  1. PR #8 保持 OPEN，任何 AI Agent 不得合并 PR #8。
  2. GitHub Support 尚未完成服务端历史清理前，不允许合并 PR #8。
  3. GitHub Support 清理完成后，必须重新验证旧提交 `2342828852abee43ab56610e7d1fa91a02310bfe` 和相关 9 个原始命令日志是否已经不可访问。
  4. 只有获得可核验证据，才能将 P2-01 标记为关闭。
  5. 不允许通过 Cherry-pick、创建替代 PR、强制推送、绕过 PR #8 等方式规避该门禁。
  6. T1-04 可以继续独立审计，但不能通过堆叠分支绕过 PR #8 将代码提前带入 main。
  7. PR #8 的合并条件必须同时包含：独立审计通过、用户验收通过、P2-01 服务端清理完成并复核旧 SHA/日志不可访问。
